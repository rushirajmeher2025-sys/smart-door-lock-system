PHASE 7 — REMOTE LOCK AND UNLOCK
============================================================

Implement Phase 7 of my Smart Door Lock System.

Objective:
Implement secure remote lock and unlock commands from the Flutter application through Firebase to the ESP32.

Required command flow:
1. The user signs in.
2. The app verifies that the user is authorized for the specific device.
3. The user requests a lock or unlock operation.
4. The backend validates the request and creates an authorized command.
5. The ESP32 receives the command.
6. The ESP32 validates the command identifier, authorization information, freshness, and processing status.
7. The ESP32 independently checks the current door state and all applicable local safety conditions.
8. The ESP32 decides whether the operation is permitted.
9. If permitted, the ESP32 actuates the servo.
10. The ESP32 verifies the resulting state as far as the hardware allows.
11. The ESP32 records the command result.
12. The app displays the confirmed result.

Safety requirements:
- Never unlock the door solely because a client writes an arbitrary value to Firebase.
- Do not treat a cloud command as an unconditional instruction to move the servo.
- Do not bypass existing local security logic.
- Reject unauthorized, expired, duplicated, malformed, or already processed commands.
- Prevent a command from being executed repeatedly after reconnection.
- Keep local keypad access functional when the network is unavailable.
- If the door is open, apply the existing safety rules and explicitly report whether the requested operation is allowed.
- Do not assume the door sensor alone can verify the bolt position.
- Display Pending, Succeeded, Rejected, Failed, or Timed Out as appropriate.
- Never show success merely because the request was submitted.
- Provide a clear reason when an operation is rejected.

Implementation:
- Create a dedicated command service in Flutter.
- Implement backend authorization and command creation.
- Implement command handling in the ESP32 firmware.
- Maintain a command identifier for each operation.
- Record processing results.
- Handle timeouts and communication failures.
- Keep the existing keypad and intrusion-alarm logic intact.

Testing:
Test unauthorized access, valid commands, duplicate commands, expired commands, door-open conditions, network loss, and recovery.

Do not claim physical safety or successful actuation without the relevant verification.

Complete Phase 7 and wait for approval.
